# Обновление допуска к рейдам

Для существующей базы PostgreSQL 16 выполнить `raid_member_eligibility.sql`
перед запуском новой версии приложения. Скрипт вручную запускается один раз;
повторный запуск допустим. Он добавляет семь nullable-колонок, не удаляет
таблицы и не изменяет значения существующих строк.

| Таблица | Новые колонки |
| --- | --- |
| `clans` | `member_list_synced_at` |
| `members` | `joined_after` |
| `raid_season_clan_member_snapshots` | `joined_at`, `joined_after`, `role`, `clan_type`, `participation_eligible` |

`members.joined_at` уже есть в текущей модели; его добавлять заново не нужно.
Если существующая база ещё не соответствует текущей версии приложения,
это нужно исправить отдельно до этого обновления.

## Порядок на сервере

Из каталога проекта с обновлёнными исходниками и `docker-compose.yml`,
в shell Linux-сервера:

```sh
docker compose stop app
docker compose exec -T db pg_dump -U gucci -d gucci > "$HOME/gucci-before-raid-eligibility.sql"
docker compose exec -T db psql -U gucci -d gucci -v ON_ERROR_STOP=1 < sql/raid_member_eligibility.sql
docker compose up -d --build app
docker compose logs --tail=100 app
```

Имена сервисов, базы и пользователя взяты из текущего `docker-compose.yml`.
Если на сервере они отличаются, подставить серверные значения.
Каждую команду выполнять после успешного завершения предыдущей.
При ошибке миграции новую версию приложения не запускать.

Сейчас настроено `ddl-auto: update`, поэтому Hibernate также может добавить
эти nullable-колонки при запуске. Для серверной базы порядок выше позволяет
применить и проверить изменение схемы заранее. Новых зависимостей,
переменных окружения и настроек Docker это обновление не требует.

## Поведение после обновления

- Во время активного рейда состав пополняется и допуск пересматривается
  по свежей полной синхронизации клана. Ушедшие игроки из снимка не удаляются.
- Из `/raidmissed` исключаются игроки без атак, для которых подтверждено:
  вступление после начала рейда, обычная роль `member` и открытый клан `open`.
  Те же исключения применяются в расчёте рейтинга.
- Старейшина (`admin`), соруководитель (`coLeader`), глава (`leader`), а также
  участники закрытого клана или клана по приглашению под это ограничение
  не попадают. Уже подтверждённая возможность атаковать сохраняется даже
  при последующем понижении роли или повторном вступлении.
- `joined_at` — время обнаружения вступления ботом. `joined_after` — время
  предыдущего полного наблюдения состава, в котором игрок ещё отсутствовал.
  Только отсутствие, подтверждённое уже после начала рейда, доказывает
  позднее вступление. Время наблюдения фиксируется перед запросом API.
- Первичная загрузка состава и вступление около границы начала рейда могут
  оставить допуск неизвестным. `participation_eligible = NULL` сохраняет
  прежнее включение игрока в отчёт и рейтинг; это не доказанное отсутствие допуска.
- Исторические снимки после миграции остаются с неизвестными новыми полями.
  Завершённые сезоны не пересчитываются по текущему составу. Старые списки
  без атак автоматически исправить без исторических данных нельзя.
  Новые подтверждения начинают накапливаться после обновления.

Правило допуска проверено 19.10.2026 по
[официальным примечаниям Supercell от 15.06.2026](https://supercell.com/en/games/clashofclans/blog/release-notes/the-anime-fury-update-is-here/),
раздел Clan Capital Improvements. Синтаксис миграции соответствует
[документации PostgreSQL 16](https://www.postgresql.org/docs/16/sql-altertable.html).
